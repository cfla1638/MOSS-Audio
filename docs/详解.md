## 1. 先记住整条主线

MOSS-Audio 的核心数据流可以压缩成：

```text
原始波形
[audio_samples]
    │
    ▼
Whisper 风格 Log-Mel 特征
[128, T_mel]
    │
    │ 约 100 帧 / 秒
    ▼
按最多 400 Mel 帧分块
[C, 128, <=400]
    │
    ▼
3 × Conv2d(stride=2,2)
[C, 480, 16, ceil(T_chunk/8)]
    │
    ▼
频率维 + 卷积通道维展平
[C, T_audio, 480×16=7680]
    │
    ▼
stem_proj: 7680 → 1280
[C, T_audio, 1280]
    │
    ▼
32 层 WhisperEncoderLayer
[C, T_audio, 1280]
    │
    ▼
去除 chunk padding + 拼接
[1, total_audio_tokens, 1280]
    │
    ▼
GatedMLP Audio Adapter
1280 → 8192 → 4096
[1, total_audio_tokens, 4096]
    │
    ▼
替换 Qwen3 输入序列中的 <|AUDIO|> embedding
[B, S, 4096]
    │
    ▼
36 层 Qwen3 Decoder
[B, S, 4096]
    │
    ▼
lm_head
[B, S, 151936]
```

对 8B 版本，最重要的几个维度是：

| 名称 | 数值 | 含义 |
|---|---:|---|
| Mel bins | 128 | 音频频率特征维 |
| Conv channels | 480 | 三层二维卷积的通道数 |
| Audio encoder hidden size | 1280 | 音频 Transformer 主维度 |
| Audio encoder FFN | 5120 | Whisper Encoder FFN 中间维 |
| Audio encoder layers | 32 | 音频 Transformer 层数 |
| Audio encoder heads | 20 | 每头 64 维 |
| Adapter hidden size | 8192 | 音频→语言空间适配器中间维 |
| Qwen3 hidden size | 4096 | 主干语言模型隐藏维 |
| Qwen3 FFN | 12288 | Qwen3 MLP 中间维 |
| Qwen3 layers | 36 | 主干层数 |
| Qwen3 attention heads | 32 | Query heads |
| Qwen3 KV heads | 8 | GQA 的 Key/Value heads |
| Qwen3 head dim | 128 | 每个 attention head 的维度 |
| Vocabulary size | 151936 | 最终 logits 的最后一维 |

# 3. 记号约定

本文使用：

```text
B      = language batch size
A      = audio_count，一条 prompt 中的音频段数
N      = 原始波形采样点数
Tmel   = Mel 时间帧数
C      = total_chunks
Tc     = 一个 chunk 的 Mel 帧数
Ta     = 一个 chunk 卷积后的 audio token 数
Taudio = 所有音频有效 audio token 总数
S      = Qwen3 的完整输入序列长度
Denc   = 1280
Dllm   = 4096
```

一个非常重要的区别：

```text
A = audio_count
B = language batch size
```

当前 Processor 通常构造：

```text
B = 1
```

但一条 prompt 可以包含多段音频：

```text
A >= 1
```

而音频编码器最后会把这些音频块全部打包成：

```text
[1, total_audio_tokens, 1280]
```

这里第一维的 `1` **不再表示 audio_count**。

# 4. 第 0 阶段：原始波形 → Mel 特征

相关代码：

```text
src/processing_moss_audio.py
    MelConfig
    _get_whisper_feature_extractor()
    _extract_mel()
```

默认配置：

```text
sampling_rate = 16000
n_fft         = 400
hop_length    = 160
mel_dim       = 128
dtype         = bfloat16
```

因此输入单声道波形：

```text
[N]
```

先加一个临时 batch 维：

```text
[1, N]
```

随后通过 `WhisperFeatureExtractor` 得到：

```text
[1, 128, Tmel]
```

去掉单段 batch 轴：

```text
[128, Tmel]
```

## 4.1 时间长度大约是多少？

Hop length 是 160，而采样率为 16000：

```text
16000 / 160 = 100
```

因此约为：

```text
100 Mel frames / second
```

也就是说：

```text
1 秒音频   ≈ 100 帧
4 秒音频   ≈ 400 帧
10 秒音频  ≈ 1000 帧
30 秒音频  ≈ 3000 帧
```

之后三次 stride=2 下采样，所以最终约为：

```text
100 / 8 = 12.5 audio tokens / second
```

这就是 MOSS-Audio 文档中 12.5 Hz 音频表示的直接来源。

# 5. Processor 如何组织多段音频

对于 A 段音频，每一段先各自得到：

```text
[128, Tmel_i]
```

然后右侧补零到最长长度：

```text
audio_data:
[A, 128, Tmax]
```

并额外保存真实长度：

```text
audio_data_seqlens:
[A]
```

例如两段音频：

```text
音频 1: [128, 450]
音频 2: [128, 200]
```

打包后：

```text
audio_data = [2, 128, 450]
audio_data_seqlens = [450, 200]
```

注意：

> Padding 只用于组成 tensor，后面的 Encoder 会根据 `audio_data_seqlens` 把无效区域去掉。

# 6. 音频 placeholder 的数量如何计算

Processor 里使用与 Encoder 完全相同的三次卷积长度公式：

```python
L1 = ceil(L / 2)
L2 = ceil(L1 / 2)
L3 = ceil(L2 / 2)
```

因此：

```text
audio_tokens = ceil(Tmel / 8)
```

严格地说，是连续执行 3 次：

```text
(L - 1) // 2 + 1
```

默认情况下等价于：

```text
ceil(L / 8)
```

例如：

```text
400 Mel frames → 200 → 100 → 50 audio tokens
200 Mel frames → 100 → 50 → 25 audio tokens
50  Mel frames → 25  → 13 → 7 audio tokens
```

所以 450 帧：

```text
ceil(450 / 8) = 57
```

如果按 Encoder 的 400 帧分块：

```text
400 → 50
50  → 7
总计 = 57
```

两边是一致的。

# 7. 时间标记并不会改变 audio feature 数量

`enable_time_marker=True` 时，Processor 会每 2 秒插入普通数字 token。

模型默认：

```text
12.5 audio tokens / second
```

所以每：

```text
25 audio tokens
```

插入一次时间数字。

例如 4 秒音频有 50 个 audio tokens：

```text
25 × <|AUDIO|>
"2"
25 × <|AUDIO|>
"4"
```

因此：

```text
audio feature 数量 = 50
```

但 Qwen3 输入序列长度会大于 50，因为还多了：

```text
时间数字 token
audio_bos
audio_eos
prompt 文本
对话模板 token
```

这是阅读代码时必须区分的两个长度：

```text
Taudio = 真正的音频 embedding 数量
S      = 最终多模态序列的总 token 数
```

```python
MossAudioEncoder.forward()
```

```text
n_window = 200
chunk_frames = n_window * 2 = 400
```

所以虽然配置里看到：

```text

```

实际 chunk 是：

```text
400 Mel frames
≈ 4 seconds
```

```text
Tmel = 1000
```

```text
400 + 400 + 200
```

也就是：

```text
C = 3 chunks
```

然后 `pad_sequence` 得到：

```text
[C, 128, padded_chunk_frames]
```

这个例子中：

```text
[3, 128, 400]
```

真实长度另外记录为：

```text
[400, 400, 200]
```

# 9. 最核心部分：3 层 Conv2d 后维度怎么变

这是整个 MOSS-Audio 最值得理解的一段。

Encoder 定义：

```python
Conv2d(
    in_channels=1,
    out_channels=480,
    kernel_size=(3, 3),
    stride=(2, 2),
    padding=(1, 1),
)
```

连续三层。

输入 chunk：

```text
[C, 128, Tc]
```

首先加 channel 维：

```text
[C, 1, 128, Tc]
```

这里二维卷积的两个空间轴分别是：

```text
频率轴 = 128
时间轴 = Tc
```

所以卷积是在 **时频二维平面上同时做下采样**。

---

## 9.1 Conv1

```text
输入:
[C, 1, 128, Tc]

Conv1:
1 → 480 channels
frequency: 128 → 64
time: Tc → ceil(Tc/2)

输出:
[C, 480, 64, ceil(Tc/2)]
```

如果 Tc=400：

```text
[C, 480, 64, 200]
```

---

## 9.2 Conv2

继续同时压缩频率与时间：

```text
[C, 480, 64, 200]
    ↓
[C, 480, 32, 100]
```

一般形式：

```text
[C, 480, ceil(128/4), ceil(Tc/4)]
```

---

## 9.3 Conv3

再做一次：

```text
[C, 480, 32, 100]
    ↓
[C, 480, 16, 50]
```

一般形式：

```text
[C, 480, 16, ceil(Tc/8)]
```

所以对于默认 400 帧 chunk：

```text
时间：
400 → 200 → 100 → 50

频率：
128 → 64 → 32 → 16
```

# 10. 为什么接下来突然出现 7680 维？

卷积输出：

```text
[C, 480, 16, Ta]
```

其中：

```text
Ta = ceil(Tc/8)
```

代码执行：

```python
x = x.permute(0, 3, 1, 2)
```

得到：

```text
[C, Ta, 480, 16]
```

再：

```python
flatten(2)
```

把最后两维合并：

```text
480 × 16 = 7680
```

于是：

```text
[C, Ta, 7680]
```

这一步的语义非常重要：

> 对于每一个下采样后的时间位置，把该时刻的 **480 个卷积通道 × 16 个压缩后的频率位置** 全部拼成一个向量。

也就是说：

```text
一个 audio token
=
该时间位置上的完整压缩频谱表示
=
7680 维
```

---

# 11. stem_proj：7680 → 1280

随后：

```python
self.stem_proj = nn.Linear(480 * 16, 1280)
```

因此：

```text
[C, Ta, 7680]
    ↓ Linear
[C, Ta, 1280]
```

从这里开始：

```text
时间轴 = audio token sequence
特征轴 = 1280
```

后面 32 层音频 Transformer 都不再改变主张量的外部形状。

---

# 12. 一个隐藏的配置限制：Mel bins 实际上不能随便改

代码写的是：

```python
self.stem_proj = nn.Linear(
    config.downsample_hidden_size * 16,
    config.d_model
)
```

这里 `16` 是固定的。

这个 16 来自：

```text
128 Mel bins
↓ /2
64
↓ /2
32
↓ /2
16
```

因此如果只把：

```text
num_mel_bins = 128
```

改成别的值，而不同时修改 `stem_proj`，网络就会发生维度不匹配。

所以从实际代码看：

> 当前 Encoder 结构事实上绑定了 128 Mel bins。

`stem_proj` 之后：


位置编码为：

```text
[1, Ta, 1280]
```

```text

=
```

注意这里的位置是：


# 14. 32 层 Whisper Encoder 中维度如何变化

MOSS-Audio 直接使用：

```python
transformers.models.whisper.modeling_whisper.WhisperEncoderLayer
```

配置：

```text
d_model = 1280
encoder_attention_heads = 20
encoder_ffn_dim = 5120
encoder_layers = 32
```

因此：

```text
head_dim = 1280 / 20 = 64
```

每一层的输入和输出都是：

```text
[C, Ta, 1280]
```

---

## 14.1 Self Attention 内部

概念上：

```text
输入
[C, Ta, 1280]
```

投影到 Q/K/V 后按 20 个头拆分：

```text
Q: [C, 20, Ta, 64]
K: [C, 20, Ta, 64]
V: [C, 20, Ta, 64]
```

Attention 权重：

```text
Q @ K^T
→ [C, 20, Ta, Ta]
```

加权 V：

```text
[C, 20, Ta, Ta]
×
[C, 20, Ta, 64]
→
[C, 20, Ta, 64]
```

拼回 20 个头：

```text
20 × 64 = 1280
```

得到：

```text
[C, Ta, 1280]
```

所以 Attention 不改变主隐藏状态形状。

---

## 14.2 FFN 内部

Whisper Encoder FFN：

```text
1280
 ↓ fc1
5120
 ↓ activation
5120
 ↓ fc2
1280
```

对应张量：

```text
[C, Ta, 1280]
    ↓
[C, Ta, 5120]
    ↓
[C, Ta, 1280]
```

加残差后仍然：

```text
[C, Ta, 1280]
```

因此完整的 32 层：

```text
Layer 0 : [C, Ta, 1280] → [C, Ta, 1280]
Layer 1 : [C, Ta, 1280] → [C, Ta, 1280]
...
Layer 31: [C, Ta, 1280] → [C, Ta, 1280]
```

# 15. Audio Encoder 中的 attention 不跨 4 秒 chunk

这是理解模型能力时很重要的一点。

Encoder 中不同 chunk 是：

```text
batch 维上的不同元素
```

例如 12 秒音频：

```text
chunk 0: 0~4 s
chunk 1: 4~8 s
chunk 2: 8~12 s
```

进入音频 Transformer 时类似：

```text
[3, 50, 1280]
```

因此 self-attention 是：

```text
chunk 0 内部互相注意
chunk 1 内部互相注意
chunk 2 内部互相注意
```

而不会发生：

```text
chunk 0 token ↔ chunk 2 token
```

的 Encoder self-attention。

跨 chunk 的全局融合是在后面的 Qwen3 中完成的，因为所有音频 token 会重新拼成一条序列。

# 16. DeepStack 在 Audio Encoder 中取哪些层？

配置：

```text
deepstack_encoder_layer_indexes = [8, 16, 24]
```

代码索引从 0 开始，因此实际捕获：

```text
第 9 个 Encoder layer 输出
第 17 个 Encoder layer 输出
第 25 个 Encoder layer 输出
```

每个捕获结果仍然是：

```text
[C, Ta, 1280]
```

注意：

> 捕获发生在对应 WhisperEncoderLayer 执行完成之后，但在整个 Encoder 最后的 `layer_norm` 之前。

最终主路径会执行：

```text
32 层 Encoder
→ final LayerNorm
→ out_proj
```

# 17. out_proj 在 8B 模型中实际上是 Identity

配置：

```text
d_model    = 1280
output_dim = 1280
```

代码：

```python
self.out_proj = (
    nn.Linear(d_model, output_dim)
    if output_dim != d_model
    else nn.Identity()
)
```

因此 8B-Instruct 当前：

```text
[... , 1280]
→ Identity
[... , 1280]
```

没有发生维度变化。

# 18. Chunk padding 如何被移除

所有 chunk 在批处理中被 pad 到同一个 token 长度，例如：

```text
chunk token lengths:
[50, 50, 25]
```

临时组成：

```text
[3, 50, 1280]
```

第三个 chunk 后 25 个位置是 padding。

代码用 bool mask：

```python
valid_tokens = padded_embed[padded_mask_after_cnn]
```

二维 mask 会把：

```text
chunk 轴 + chunk 内时间轴
```

展平成一个有效 token 序列：

```text
[50 + 50 + 25, 1280]
=
[125, 1280]
```

最后：

```python
unsqueeze(0)
```

得到：

```text
[1, 125, 1280]
```

一般形式：

```text
[1, total_audio_tokens, 1280]
```

---

# 19. 为什么这里第一维总是 1？

这是一个非常容易误解的地方。

Encoder 最开始可能有：

```text
[A, 128, Tmax]
```

例如 A=3 表示三段音频。

但它会：

1. 去掉每段 padding；
2. 保留原始音频边界进行 chunk；
3. 编码所有 chunk；
4. 删除 chunk padding；
5. 按原始顺序将所有有效 audio tokens 打包。

最后结果：

```text
[1, total_audio_tokens, 1280]
```

所以：

```text
第一维 1 ≠ audio_count
```

它只是给打包后的音频 token 序列补上的单例维。

# 20. Audio Adapter：1280 → 8192 → 4096

主音频特征出来后：

```text
[1, Taudio, 1280]
```

进入：

```python
GatedMLP(
    input_size=1280,
    hidden_size=8192,
    output_size=4096
)
```

GatedMLP 结构：

```python
down_proj(
    SiLU(gate_proj(x)) * up_proj(x)
)
```

两条分支：

```text
gate_proj:
[1, Taudio, 1280]
→
[1, Taudio, 8192]

up_proj:
[1, Taudio, 1280]
→
[1, Taudio, 8192]
```

逐元素相乘：

```text
[1, Taudio, 8192]
*
[1, Taudio, 8192]
=
[1, Taudio, 8192]
```

再：

```text
down_proj:
8192 → 4096
```

得到：

```text
[1, Taudio, 4096]
```

这是音频真正进入 Qwen3 之前的最后一次主维度变化。

# 21. 文本 token 和音频 token 如何进入同一个 Qwen3 序列

文本输入：

```text
input_ids:
[B, S]
```

先查 Qwen3 embedding：

```text
[B, S]
→
[B, S, 4096]
```

注意此时 `<|AUDIO|>` 也只是普通特殊 token，其 embedding 也是一个 4096 维向量。

随后：

```python
audio_input_mask = input_ids == audio_token_id
```

得到：

```text
[B, S]
```

其中只有 `<|AUDIO|>` 位置为 True。

Audio Adapter 输出：

```text
[1, Taudio, 4096]
```

然后通过：

```python
masked_scatter_
```

把这些位置原本的 token embedding 换成真正的音频 embedding。

所以：

```text
替换前:
[B, S, 4096]

替换后:
[B, S, 4096]
```

**整个序列的形状完全不变。**

变化的只是部分位置上的数值来源：

```text
文本位置:
token embedding

音频位置:
audio encoder + adapter embedding

时间标记位置:
普通数字 token embedding
```

从 Qwen3 的视角看，它收到的是统一的：

```text
[B, S, 4096]
```

# 22. 这是理解 MOSS-Audio 多模态融合的关键

MOSS-Audio 并没有在 Qwen3 里增加一个独立 cross-attention 模块。

它采用的是：

```text
audio encoder
      ↓
adapter
      ↓
转成和 text embedding 相同的 4096 维
      ↓
直接塞进 Qwen3 token sequence
```

因此进入 Qwen3 后：

```text
audio token
text token
time token
special token
```

都是同一条 causal Transformer 序列中的 token。

# 23. DeepStack 的第二条音频路径

除了最终 Audio Encoder 输出，MOSS-Audio 还取：

```text
Encoder layer 8
Encoder layer 16
Encoder layer 24
```

三个中间特征。

它们在去 padding 后分别都是：

```text
[1, Taudio, 1280]
```

每一路都有**独立** GatedMLP：

```text
1280 → 8192 → 4096
```

所以得到：

```text
DeepStack 0: [1, Taudio, 4096]
DeepStack 1: [1, Taudio, 4096]
DeepStack 2: [1, Taudio, 4096]
```

# 24. DeepStack 到底注入 Qwen3 的哪里？

代码给 Qwen3 decoder layers 注册 forward hook。

三个 Audio Encoder 中间层按顺序对应：

```text
Audio Encoder layer 8  → Qwen3 layer 0 输出
Audio Encoder layer 16 → Qwen3 layer 1 输出
Audio Encoder layer 24 → Qwen3 layer 2 输出
```

注意这里是：

```text
Qwen3 layer 执行完成
        ↓
forward hook
        ↓
只在 audio token 位置加 DeepStack residual
```

不是：

```text
进入 Qwen3 layer 之前注入
```

而是：

```text
该 Qwen3 layer 的输出之后注入
```

数学上可以理解为：

```text
H_l = QwenLayer_l(H_{l-1})

H_l[audio_positions]
    += DeepStack_l
```

完整张量始终：

```text
[B, S, 4096]
```

# 27. Qwen3 Attention：Q、K、V 的维度并不一样

Qwen3-8B 使用 GQA。

## Query

```text
q_proj:
4096 → 32 × 128 = 4096
```

所以：

```text
[B, S, 4096]
→
[B, S, 32, 128]
→ transpose
[B, 32, S, 128]
```

## Key

```text
k_proj:
4096 → 8 × 128 = 1024
```

所以：

```text
[B, S, 4096]
→
[B, S, 8, 128]
→
[B, 8, S, 128]
```

## Value

同样：

```text
[B, 8, S, 128]
```

---

# 28. 为什么 KV 只有 8 个头？

因为：

```text
num_attention_heads = 32
num_key_value_heads = 8
```

因此：

```text
32 / 8 = 4
```

每组 K/V 供 4 个 Query heads 共用。

这就是 Grouped Query Attention。

在 eager attention 逻辑里，可以概念性理解为：

```text
K/V:
[B, 8, S, 128]

repeat 4 times

→ [B, 32, S, 128]
```

随后和：

```text
Q:
[B, 32, S, 128]
```

做 attention。

---

# 29. Qwen3 Attention Score 的形状

Query：

```text
[B, 32, Sq, 128]
```

Key：

```text
[B, 32, Skv, 128]
```

所以：

```text
Q @ K^T
→
[B, 32, Sq, Skv]
```

在完整 prefill 中通常：

```text
Sq = Skv = S
```

于是：

```text
[B, 32, S, S]
```

随后乘 Value：

```text
[B, 32, S, S]
×
[B, 32, S, 128]
→
[B, 32, S, 128]
```

转置并合并 heads：

```text
[B, S, 32, 128]
→
[B, S, 4096]
```

再经过：

```text
o_proj:
4096 → 4096
```

所以 Attention 模块整体：

```text
[B, S, 4096]
→
[B, S, 4096]
```

# 30. Qwen3 MLP 的维度

Attention + residual 之后仍然：

```text
[B, S, 4096]
```

MLP 是另一套 gated MLP：

```text
gate_proj:
4096 → 12288

up_proj:
4096 → 12288
```

因此：

```text
[B, S, 4096]
→
[B, S, 12288]
```

两路相乘后仍然：

```text
[B, S, 12288]
```

最后：

```text
down_proj:
12288 → 4096
```

回到：

```text
[B, S, 4096]
```

加 residual：

```text
[B, S, 4096]
```

所以 36 层 Qwen3 的外部形状都是：

```text
Layer 0 : [B,S,4096] → [B,S,4096]
Layer 1 : [B,S,4096] → [B,S,4096]
...
Layer 35: [B,S,4096] → [B,S,4096]
```

# 31. 生成时 KV Cache 的维度

Qwen3 使用 8 个 KV heads。

因此某一层缓存的 K/V 核心形状可理解为：

```text
K cache:
[B, 8, Lcache, 128]

V cache:
[B, 8, Lcache, 128]
```

不是：

```text
[B, 32, Lcache, 128]
```

这正是 GQA 节省 KV cache 显存的重要原因之一。

在 attention 计算阶段，再按需要把 8 个 KV heads 与 32 个 query heads 对齐。

# 36. 为什么 Audio Encoder 内部是 1280，而 Qwen 是 4096？

可以把它理解成两个不同表示空间：

```text
Audio latent space:
1280 dimensions

Language latent space:
4096 dimensions
```

Audio Encoder 的任务是高效表示：

```text
语音内容
音色
节奏
背景声
音乐
时频结构
```

而 Qwen3 主干需要在其原有的语言 hidden space 中进行统一推理。

因此中间的 Adapter 实际承担：

```text
audio representation
      ↓
modality alignment
      ↓
language-model representation
```

即：

```text
1280 → 4096
```

---

# 37. 为什么 Adapter 中间层反而是 8192？

Adapter 不是一个简单：

```text
Linear(1280, 4096)
```

而是一个 gated MLP：

```text
1280
 ↙   ↘
8192 8192
  \   /
 elementwise gate
    ↓
  8192
    ↓
  4096
```

因此它不仅做维度匹配，也具有较强的非线性映射能力。

---

# 38. 音频 Encoder 与 Qwen3 的注意力有一个根本区别

## Audio Encoder

```text
WhisperEncoderLayer
non-causal self-attention
```

一个 4 秒 chunk 内：

```text
前面的 token 可以看到后面的 token
后面的 token 也可以看到前面的 token
```

即双向声学编码。

## Qwen3

```text
causal decoder self-attention
```

序列中位置只能看当前和之前的 token。

因此整体结构可以理解成：

```text
局部双向音频理解
        ↓
打包为 audio tokens
        ↓
全局因果多模态推理 / 文本生成
```

---

# 39. Chunking 带来的结构性含义

因为 Audio Encoder 是 4 秒独立编码：

```text
0~4 秒    ┐
4~8 秒    ├→ 各自独立 Audio Encoder
8~12 秒   ┘
```

随后才拼接：

```text
audio token 0 ... audio token N
```

进入 Qwen3。

所以：

> Audio Encoder 更像局部声学特征提取器，而跨越很多秒、很多 chunk 的长程关系主要依赖后面的 Qwen3 主干。

这有助于理解为什么模型可以处理较长音频，同时不让 Audio Encoder 在整个音频长度上承担平方复杂度 attention。

---

# 40. 默认 400 帧 chunk 为什么很巧妙？

因为：

```text
400 / 8 = 50
```

恰好整除。

Processor 预测 placeholder 数量使用：

```text
ceil(Tmel / 8)
```

Encoder 却实际先分块，再分别：

```text
ceil(Tchunk / 8)
```

一般来说：

```text
ceil(a/8) + ceil(b/8)
```

不一定等于：

```text
ceil((a+b)/8)
```

但默认 chunk：

```text
400
```

是 8 的倍数，所以完整 chunk 不会引入额外 rounding error。

因此默认设计能保证：

```text
Processor 生成的 <|AUDIO|> 数量
==
Encoder 真正生成的 audio feature 数量
```

如果随意把 chunk size 改成不是 8 的倍数，需要特别小心。

---

# 41. DeepStack 为什么有意义？

如果只取 Audio Encoder 最后一层：

```text
Layer 31
```

它往往更偏高层语义。

MOSS-Audio 额外保留：

```text
Layer 8
Layer 16
Layer 24
```

可以让 Qwen3 早期层继续接收到不同抽象层次的音频信息。

可以粗略理解为：

```text
Layer 8
更偏局部 / 低中层声学结构

Layer 16
中层表示

Layer 24
更高层音频语义

Layer 31
最终主音频 embedding
```

这里“低层/高层”的具体语义不能仅靠代码严格证明，但 DeepStack 的结构目的就是避免只依赖最后一层表示。

# 43. 阅读代码时最容易混淆的 10 个点

## 1. `audio_count` 不是 language batch size

Processor 的一条文本样本可以带多段音频。

---

## 2. `n_window=200` 不代表 chunk 是 200 帧

代码：

```python
chunk_frames = n_window * 2
```

所以默认是 400 帧。

---

## 3. 3 层卷积既压时间，也压频率

不是单纯：

```text
T → T/8
```

而是：

```text
128 × T
→
16 × T/8
```

---

## 4. 7680 不是 Transformer hidden size

它只是：

```text
480 conv channels × 16 remaining frequency bins
```

展平后的临时维度。

---

## 5. 真正的 Audio Encoder hidden size 是 1280

从 `stem_proj` 之后开始一直保持 1280。

---

## 6. Audio Encoder 的输出 `1` 不是 audio_count

```text
[1, total_audio_tokens, 1280]
```

已经是多个 chunk / 多段音频打包后的形式。

---

## 7. Audio Adapter 不改变 token 数量

它只改变：

```text
1280 → 4096
```

时间长度完全保持。

---

## 8. 音频并不是作为 Qwen3 的 cross-attention memory

它被直接变成 Qwen3 embedding 序列中的 token。

---

## 9. 时间数字不是 audio token

例如 `"2"`、`"4"` 仍然走普通文本 embedding。

---

## 10. DeepStack 是 residual injection

不是把特征拼接到 hidden dimension：

```text
4096 + 4096
```

这里的 `+` 是逐元素相加，因此结果仍然：

```text
4096
```

不是：

```text
8192
```

# 46. 最后用一句话记住整个模型

MOSS-Audio-8B 的核心维度链可以记成：

```text
Waveform
→ 128-bin Mel
→ 3×Conv2d
→ 480×16 = 7680
→ 1280-d Audio Transformer
→ 8192-d gated adapter
→ 4096-d Qwen3 token space
→ 36-layer Qwen3
→ 151936-way vocabulary logits
```

时间长度链则记成：

```text
16000 samples / s
→ 100 Mel frames / s
→ 12.5 audio tokens / s
```

因此，一个最简洁的模型认识是：

> **MOSS-Audio 先把每约 80 ms 的音频压缩成一个 1280 维声学 token，再用 Adapter 映射成 4096 维 Qwen3 token；从此以后，音频和文本就在同一个 Qwen3 序列里进行统一建模。**
